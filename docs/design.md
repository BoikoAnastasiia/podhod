# Подход — Design

**Date:** 2026-08-04
**Status:** Approved, ready for planning

A personal strength-training app: you define programs with progression rules, the
app computes each session's targets from your history and walks you through it set
by set. Portfolio piece, bilingual RU/EN, built on a stack deliberately distinct
from the author's three existing Supabase projects.

The name is the Russian word for a set — and for "an approach."

---

## 1. Scope

**In scope for v1**

- Program-driven training: build a program, follow it, log every set.
- A progression engine that computes today's target weight and reps from history.
- The full 1,324-exercise library, browsable and searchable, in Russian and English.
- Open signup with real authentication.
- History and progress views.

**Explicitly out of scope**

Supersets and circuits · auto-generated warmup sets · body measurements ·
nutrition · social and sharing · a template marketplace · offline write sync ·
wearable and Health integrations.

Supersets are the most likely thing to want back. The schema accommodates them
later through a nullable `group_id` on `program_exercises` — an additive
migration, not a redesign.

**Wearables were investigated and rejected, not overlooked.** Garmin does not
expose the `addSet()` capability required to write set-level data into FIT files,
so third-party apps cannot push completed strength sessions into Garmin Connect;
Hevy was approved for integration and still only received a restricted one that
cannot do this. Apple HealthKit has no web API whatsoever — a PWA cannot reach it
under any configuration. Reading *from* Garmin is possible via the Connect
Developer Program but requires application approval and, for some metrics, a
business case or licence fee. Aggregators (Terra, Junction) start around
$399/month. None of this is worth v1. The README should say so explicitly.

## 2. Stack

| Layer | Choice |
|---|---|
| Client | Vite 7, React 19, TanStack Router (file-based), TanStack Query |
| Styling | Tailwind CSS 4 + shadcn/ui (Radix primitives) |
| Motion | GSAP 3 + `@gsap/react` (`useGSAP`), Flip plugin for shared elements |
| API | Hono on Cloudflare Workers |
| Database | Cloudflare D1 (SQLite) + Drizzle ORM with migrations |
| Auth | Better Auth, Drizzle adapter, sessions in D1 |
| Deploy | Wrangler, GitHub Actions |

**One Worker serves both.** `apps/web` builds to static assets served by the same
Worker that runs the Hono API, so `/api/*` is same-origin. This removes CORS
entirely and lets Better Auth use plain `HttpOnly; SameSite=Lax` cookies rather
than a token exchange.

```
apps/web        React 19 SPA
apps/api        Hono · Better Auth · Drizzle/D1 · serves web's assets
packages/core   progression engine — pure TS, zero dependencies, zero I/O
packages/schema Zod schemas shared by client and server
packages/i18n   UI strings + RU taxonomy dictionary
data/           build scripts and committed seed artifacts
```

`packages/core` is a deliberate boundary. The progression rules are pure functions
of `(scheme, recent performances) → target`. No database, no clock, no fetch. The
API calls them; the client calls them for optimistic previews; the tests are plain
tables of input and expected output. It is the module a reviewer will actually
read, and it should be understandable in one sitting.

## 3. Data model

D1 / SQLite via Drizzle.

### Library — seeded, read-only

**`exercises`** — language-neutral fields only
`id` (TEXT PK, `"0001"`) · `body_part` · `equipment` · `target` · `muscle_group` ·
`secondary_muscles` (JSON) · `media_id` · `image_path` · `gif_path`

**`attribution` is not a column.** All 1,324 records carry the identical string
`"© Gym visual — https://gymvisual.com/"`, so it lives once as a constant in
`packages/core` rather than 1,324 times in the database.

**`exercise_translations`** — PK `(exercise_id, lang)`
`name` · `steps` (JSON array)

Russian names live here beside Russian instructions, so adding a third language is
a seed change rather than a schema change.

### User data

- Better Auth's `users`, `sessions`, `accounts`, `verifications` (generated by its
  Drizzle adapter).
- **`user_settings`** — `locale` · `units` (kg\|lb) · `plate_increment_kg` ·
  `default_rest_seconds` · `theme`
- **`programs`** — `name` · `notes` · `is_active` · `created_at` · `archived_at`.
  At most one program per user has `is_active = 1`.
- **`program_days`** — `program_id` · `position` · `name` (`"Push A"`)
- **`program_exercises`** — `program_day_id` · `exercise_id` · `position` ·
  `scheme_type` · `scheme_config` (JSON) · `rest_seconds` · `notes`
- **`workouts`** — one training session. `program_day_id` nullable, so freestyle
  sessions work. `started_at` · `finished_at` · `status`
- **`workout_entries`** — `exercise_id` · `position` · **`planned`** (JSON snapshot)
- **`set_logs`** — `set_index` · `weight_kg` · `reps` · `rpe` · `is_warmup` ·
  `completed_at`

### Three decisions worth defending

**The plan is snapshotted into the workout at start.** Programs are edited
constantly. If history pointed at live program rows, last March's session would
silently rewrite itself every time an increment changed.
`workout_entries.planned` freezes what the app asked for; `set_logs` records what
happened. Planned versus actual stays truthful permanently.

**`set_logs` carries denormalized `user_id` and `exercise_id`.** Both are reachable
via `workout_entries → workouts`, but the hottest query in the app — "my last N
performances of this exercise," which every target computation needs — becomes a
single indexed single-table read instead of a two-join walk. This is the only
denormalization accepted; everything else stays normalized.

**Weight is always stored in kilograms as REAL.** Pounds are a display conversion
only. Mixed-unit storage is the standard way these apps corrupt their own history.

### Day sequencing

"Today" is **rotation-based, not calendar-based.** The next day is the one
following the `program_days.position` of the most recently completed workout in the
active program, wrapping to the first day. Nothing is scheduled to weekdays,
nothing is ever "missed," and a program can be followed at whatever cadence real
life allows. With no completed workouts yet, the next day is `position = 0`.

Freestyle sessions (`program_day_id IS NULL`) do not advance the rotation.

### Personal records

PRs are **computed, never stored.** For a given user and exercise, a set is a PR if
its estimated one-rep max exceeds every prior set's, using Epley:
`e1RM = weight × (1 + reps / 30)`. Warmup sets are excluded. This is one indexed
query against `set_logs` thanks to the denormalized columns above, so a
`personal_records` table would be cache with no cache-invalidation upside.

`set_logs.is_warmup` exists so warmups can be logged and then excluded from PR,
tonnage and progression calculations. Auto-*generating* warmup sets is out of scope;
recording one you did yourself is not.

### Media

The database stores `media_id` and relative paths only. URLs are constructed at
render time from a single environment variable, defaulting to jsDelivr against the
source repository. The `attribution` string renders on every exercise detail view.

**Licensing:** the dataset's *data* is MIT, but the images and GIFs are © Gym
visual, redistributed in the source repo under a separate written permission that
explicitly does not extend to downstream users — "cloning this repo is not a
licence." Media must stay at 180×180 and carry attribution. If the media is ever
licensed properly, the environment variable repoints at R2 with no data migration.

## 4. Progression engine

`packages/core`. Pure: no `Date`, no I/O, no randomness.

```ts
type Scheme =
  | { kind: 'fixed';  sets; reps; weightKg }
  | { kind: 'linear'; sets; reps; incrementKg; failuresBeforeDeload; deloadPct }
  | { kind: 'double'; sets; repLow; repHigh; incrementKg }
  | { kind: 'rpe';    sets; reps; targetRpe; adjustPct }

type Performance = {                      // one past session of one exercise
  sets: { reps: number; weightKg: number; rpe?: number }[]   // working sets only
  targetWeightKg: number                  // what was asked of you that day
  targetReps: number
}

type Target =
  | { needsBaseline: true }
  | { needsBaseline: false; sets: number; reps: number; weightKg: number
      delta: number                       // change vs. last session, drives the chip
      reason: 'progressed' | 'held' | 'deloaded' }

nextTarget(scheme, history: Performance[], { plateIncrementKg }): Target
```

`history` arrives most-recent-first and contains working sets only — warmups are
filtered by the caller, so the engine never has to know what a warmup is. Ordering
is the only temporal information it needs, which is what keeps it free of a clock.

`reason` exists so the UI can explain itself: a deload should say *why* it dropped
your weight rather than silently reducing it.

- **fixed** — constant.
- **linear** — all sets hit at target weight → `+incrementKg`. Otherwise count the
  consecutive-failure streak; at `failuresBeforeDeload`, apply
  `weight × (1 − deloadPct)` and reset the streak.
- **double** — hold the weight inside the rep range. When *every* set reached
  `repHigh`, add `incrementKg` and reset the target to `repLow`. Otherwise hold the
  weight and set the target to `min(repHigh, lowestRepsAchieved + 1)` — you chase
  the weakest set, which is what actually drives the range upward.
- **rpe** — mean RPE of working sets below `targetRpe − 1` → increase by
  `adjustPct`; above `targetRpe + 0.5` → decrease; otherwise hold.

Every computed weight passes through
`roundToIncrement(kg, plateIncrementKg, 'down')`, because 82.4 kg cannot be loaded.

**With no history the engine returns `needsBaseline: true`** rather than guessing,
and the UI asks for a starting weight once. This is the edge case where naive
implementations quietly emit a 0 kg target.

The API calls `nextTarget` when a workout starts and snapshots the result into
`workout_entries.planned`. The client imports the same module to preview upcoming
targets without a round trip.

## 5. Visual system

```
canvas    #F5F5F3  /  #0E0E0E        surface  #FFFFFF  /  #1A1A1A
ink       #111111  /  #F2F2F0        muted    #8A8A85
accent    #D4F14A  (acid lime)
radius    cards 24 · rows 16 · buttons full pill
```

**The accent never appears for decoration.** It marks exactly three things: a
completed set, a personal record, and a weight the engine raised. Nothing else. A
glance then tells you what you achieved without reading. This is the single rule
that makes a three-token palette feel designed rather than sparse.

**Text on lime is always near-black, never white.** `#D4F14A` is too luminous for
white text in either theme.

**All numerals use `font-variant-numeric: tabular-nums`.** Proportional figures
make set rows jitter as weights change.

**Tailwind house rule: arbitrary values are banned.** No `bg-[#D4F14A]`, no
`p-[13px]`. Every utility resolves to a `@theme` token. This is what prevents the
system from decaying into forty one-off hex codes, and it is enforced in review.

### Constraints the design must absorb

**Media is 180×180 and cannot be larger.** The app therefore cannot be
photography-led the way most fitness UIs are. GIFs sit in a fixed 180px frame on a
neutral card, and the identity comes from typography, colour and motion instead.
This is a constraint worth leaning into — it produces something cleaner and more
distinctive than the photo-collage house style.

**Russian is roughly 15% longer and exercise names are severe** — "Жим штанги лежа
узким хватом" against "Close-grip bench press." Every card, row and button is
verified at Russian length, not designed at English length and translated
afterwards.

**Gym ergonomics.** Arm's length, sweaty hands, sometimes gloves. Minimum 56px row
height, steppers no smaller than 44px.

### Motion

GSAP 3 via `@gsap/react`. All animation goes through the **`useGSAP()` hook** — a
drop-in replacement for `useLayoutEffect` that reverts every tween, timeline and
plugin instance on unmount via `gsap.context()`, and is safe under React's
development double-invocation. Selectors are scoped with the hook's `scope` ref;
event handlers are wrapped in `contextSafe()` so callbacks no-op after unmount.

GSAP was chosen over framer-motion partly to widen the author's toolset, but it is
also the better fit here:

- **The rest timer ring.** The timer is timestamp-driven so it survives the screen
  locking. A GSAP timeline is *seekable* — on resume, `tl.seek(elapsed)` renders the
  exact correct frame. This is the capability framer-motion lacks and the reason the
  choice is technical rather than cosmetic.
- **Set completion.** An orchestrated sequence — index badge scale, row fill
  sweeping left to right, checkmark drawn with DrawSVG — expressed as one timeline
  with explicit offsets.
- **Personal records.** SplitText on the numeral plus a staggered accent burst.
- **Tonnage counters.** GSAP tweens arbitrary numeric values, so counting up to
  `3,590 kg` is one call.

Every formerly paid plugin (SplitText, MorphSVG, DrawSVG, ScrollTrigger, Flip) has
been free for commercial use since April 2025, with no attribution requirement.

**Route transitions use GSAP Flip, not the View Transitions API.** Two reasons:
view transitions cannot be interrupted — navigate again mid-flight and the
animation snaps, which is visible in a session player where exercises are tapped
through quickly — and GSAP timelines are interruptible and reversible. (The API is
also only Baseline *newly* available, since Firefox 144 in October 2025.)

The pattern needs no presence layer, because Flip animates from a **recorded state
object rather than a live element**:

```
1. on tap        Flip.getState('.exercise-thumb')  → stash in a store
2. navigate      route swaps normally
3. on mount      useGSAP → Flip.from(stashedState, { … })
```

The outgoing route therefore never has to stay mounted, and TanStack Router's
lifecycle is left alone. Used for the library thumbnail → detail hero morph and the
Today card → session player morph.

**Animation is enter-only; there are no exit transitions.** GSAP has no
`AnimatePresence` equivalent, and rather than build a delayed-unmount helper, the
app simply doesn't animate content out. This is both simpler and better — outgoing
content that lingers only delays what the user asked for.

Flip is additionally used for drag-to-reorder in the program editor.

**Reduced motion is non-negotiable.** All motion is declared inside
`gsap.matchMedia()` with a `(prefers-reduced-motion: reduce)` branch that holds
end states rather than animating to them. State must never be conveyed by motion
alone — the accent colour is always the primary signal, motion only its emphasis.

## 6. Screens

```
/                  Today — next day, computed targets, Start workout
/session/:id       the session player
/programs          list          /programs/:id   day + scheme editor
/library           search+filter /library/:id    GIF, steps, your history
/history           by week       /history/:id    summary, tonnage, PRs
/progress          estimated 1RM per exercise, weekly tonnage by muscle group
/settings          locale, units, plate increment, rest, theme, account
```

### The session player

Everything else exists to serve this screen.

Exercise name and `3 / 5` at the top. The 180px GIF in a fixed frame, instructions
collapsed by default. Then the line that justifies the architecture:

> **Target: 4 × 8 @ 82.5 kg**  `+2.5 kg` ← accent chip
> *Last time: 4 × 8 @ 80 kg*

Below, the set rows: a black index badge, reps and weight as **steppers rather than
text inputs** — incrementing by the configured plate step, long-press to
accelerate, tap the numeral itself for a keypad fallback. A gym is the worst
possible place for a numeric keyboard.

**The ✓ is the only control that writes.** One tap logs one set, the row turns
accent, and the rest timer starts automatically — a ring counting down from a
**stored timestamp rather than a `setInterval`**, so locking the phone cannot
corrupt it. Wake Lock holds the screen during a set.

### The retry outbox

The app is online-only by decision: no offline sync, no conflict resolution. But
set writes go through a small localStorage-backed outbox (~40 lines) that holds and
retries a failed POST. Losing a set you actually lifted because the Wi-Fi blinked
is the one failure this app must never have, and this is cheap insurance rather
than a change of architecture.

## 7. Internationalisation

Only `instructions` and `instruction_steps` are multilingual in the source dataset.
`name`, `body_part`, `equipment`, `target` and `muscle_group` are English-only
strings, so Russian support is a build problem, not a filtering problem.

```
pnpm data:fetch    17 MB source → gitignored cache
pnpm data:build    strip to en+ru → data/exercises.seed.json  (2.1 MB, committed)
pnpm db:seed       Drizzle bulk insert → local and remote D1
```

`data/taxonomy.ru.json` — **exactly 85 distinct terms** (10 body parts, 28
equipment, 19 targets, 29 muscle groups, 40 secondary muscles, overlapping) — is
**hand-curated**, because that vocabulary appears in every filter chip and a
machine translation of "waist" or "leverage machine" into gym Russian will be wrong
in a way you notice daily. A test asserts every taxonomy value present in the seed
has a Russian entry, so the dictionary cannot silently fall behind the data.

**Exercise names ship in English in both locales.** Only `instructions` and
`instruction_steps` are multilingual upstream; names and the whole taxonomy are
English-only strings. The taxonomy is small enough to translate by hand (85
terms), the names are not (1,324). Rather than machine-translate them, the app
ships English names — which Russian lifters commonly use anyway — and carries
Russian everywhere else: UI strings, instruction steps, and every filter chip.

**The project has no AI or LLM dependency**, at runtime or at build time.

This is reversible without a migration: `exercise_translations` already stores a
name per language, so Russian names can be filled in by hand over time.

UI strings are a typed dictionary in `packages/i18n` using `Intl.PluralRules` for
Russian's three plural forms (подход / подхода / подходов). No i18n library for
~150 strings.

## 8. Errors, testing, delivery

Zod schemas in `packages/schema` are shared by both sides; Hono validates with
`zValidator` and returns a typed envelope `{ error: { code, message } }`. Mutations
are optimistic through TanStack Query with rollback on failure.

| Target | Approach |
|---|---|
| `packages/core` | Table-driven Vitest. Full branch coverage on the engine. |
| `apps/api` | Integration tests against a **real Worker and real D1** via `@cloudflare/vitest-pool-workers`, migrations applied per suite. |
| `apps/web` | One Playwright smoke test on the flow that must never break: start workout → log three sets → finish → appears in history. |

GitHub Actions runs typecheck, lint and all three suites, then `wrangler deploy` on
green.

## 9. Phases

Each phase ends deployable, and each gets its **own implementation plan** — this
spec is deliberately larger than one plan's worth of work.

1. **Foundation** — monorepo, D1 + Drizzle + migrations, seed pipeline including
   Russian names, Better Auth, library browse and search.
   *Ships as a usable bilingual exercise encyclopedia.*
2. **Programs** — CRUD, day editor, exercise picker, scheme editor.
3. **Engine** — `packages/core` built test-first, wired into target computation.
4. **Session player** — set logging, rest timer, outbox. The largest phase.
5. **History and progress** — charts, personal records, weekly tonnage.
6. **Polish** — dark mode, motion, Russian layout pass at layout extremes, PWA
   install.
