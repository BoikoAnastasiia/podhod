# Подход Phase 3a — Programs Data & API Implementation Plan

**Goal:** Store training programs and serve them: `programs`, `program_days` and `program_exercises` tables, and an authenticated CRUD API over them, including reordering and per-exercise scheme configuration.

**Architecture:** Three tables under a single owner. Every route is session-gated and scoped by `user_id`; ownership of a day or an exercise row is proven by joining back to `programs`, never by trusting an id from the request. Scheme configuration is validated with the `schemeSchema` the engine already defines, so a row that reaches `nextTarget()` cannot be malformed.

**Tech Stack:** Hono · Cloudflare Workers · D1 · Drizzle ORM · Zod 4 · Vitest 4 + `@cloudflare/vitest-pool-workers`

**Scope note:** No UI. Plan 3b builds `/programs` and the day/scheme editors against this API. `workouts`, `workout_entries` and `set_logs` belong to the session-player phase and are not created here — a program is a *plan*, and nothing in this phase records anything performed.

**Design note:** Visual design is deliberately untouched in this phase and the next. The owner has parked it until the logic is complete; nothing here should introduce new tokens, components or layout decisions.

## Global Constraints

- **Every route requires a session** via `requireSession()`, and every query filters by the session's `user.id`. There is no route in this phase that a signed-out caller can reach.
- **Ownership is proven, never assumed.** A `programDayId` in a request body is attacker-controlled. Reads and writes on days and exercises join through `programs` and filter on `user_id`; a row belonging to someone else must return **404**, not 403 — a 403 confirms the row exists.
- **At most one active program per user**, enforced by a partial unique index in SQL, not by application code alone.
- `scheme_config` is stored as TEXT holding JSON validated by `schemeSchema` from `@podhod/schema` on the way in, and parsed with `parseSchemeConfig` on the way out.
- Positions are contiguous integers from 0 within their parent. Reordering is a single endpoint taking the complete ordered list of ids, not a per-row swap.
- Deletes cascade in SQL (`ON DELETE CASCADE`), so removing a program cannot orphan days or exercises.
- The shared error envelope from `packages/schema` (`errorResponseSchema`) is the only error shape any route returns.
- `pnpm --filter <pkg> run <script>` — always with `run`.
- No new dependencies.

Append to `apps/api/src/db/schema.ts`:

```ts
/**
 * A training program: an ordered set of days, each an ordered set of exercises
 * with a progression scheme. Programs are edited constantly, which is why a
 * workout snapshots its plan rather than pointing at these rows — see
 * docs/design.md §3.
 *
 * `archivedAt` rather than a delete: history will reference programs by name
 * long after they stop being used, and losing that context to a DELETE would
 * make old sessions unreadable.
 */
export const programs = sqliteTable(
  "programs",
  {
    id: text("id").primaryKey(),
    userId: text("user_id")
      .notNull()
      .references(() => user.id, { onDelete: "cascade" }),
    name: text("name").notNull(),
    notes: text("notes"),
    // 0/1 rather than a boolean: D1 is SQLite and the partial unique index
    // below is written against the integer.
    isActive: integer("is_active").notNull().default(0),
    createdAt: integer("created_at").notNull(),
    archivedAt: integer("archived_at"),
  },
  (t) => [index("idx_programs_user").on(t.userId)],
);

export const programDays = sqliteTable(
  "program_days",
  {
    id: text("id").primaryKey(),
    programId: text("program_id")
      .notNull()
      .references(() => programs.id, { onDelete: "cascade" }),
    position: integer("position").notNull(),
    name: text("name").notNull(),
  },
  (t) => [index("idx_program_days_program").on(t.programId, t.position)],
);

/**
 * `schemeConfig` is TEXT holding JSON rather than separate columns per scheme:
 * the four schemes share almost no fields, so columns would be mostly NULL and
 * every read would need to know which ones apply. It is validated by
 * schemeSchema on the way in and parsed with parseSchemeConfig on the way out,
 * so the JSON is never trusted just because it is already stored.
 */
export const programExercises = sqliteTable(
  "program_exercises",
  {
    id: text("id").primaryKey(),
    programDayId: text("program_day_id")
      .notNull()
      .references(() => programDays.id, { onDelete: "cascade" }),
    exerciseId: text("exercise_id")
      .notNull()
      .references(() => exercises.id),
    position: integer("position").notNull(),
    schemeType: text("scheme_type").notNull(),
    schemeConfig: text("scheme_config").notNull(),
    restSeconds: integer("rest_seconds"),
    notes: text("notes"),
  },
  (t) => [index("idx_program_exercises_day").on(t.programDayId, t.position)],
);
```

- [ ] **Step 3: Add the partial unique index by hand**

drizzle-kit does not emit partial indexes. Append to the generated `0002_*.sql`:

```sql
--> statement-breakpoint
-- At most one active program per user. Enforced here rather than in the
-- handler because two concurrent activations would both pass an application
-- check and both write; a unique index makes the second one fail.
CREATE UNIQUE INDEX `idx_programs_one_active_per_user`
  ON `programs` (`user_id`) WHERE `is_active` = 1;
```

The `--> statement-breakpoint` marker is required — the migration runner splits on it, and without it this statement is appended to the previous one and silently never runs as its own statement.

```ts
import { z } from "zod";
import { schemeSchema } from "./scheme.js";

const name = z.string().trim().min(1).max(80);
const notes = z.string().trim().max(2000).nullish();
const id = z.string().min(1).max(64);

export const createProgramSchema = z.object({ name, notes });
export const updateProgramSchema = z.object({
  name: name.optional(),
  notes,
  // Activation goes through this same endpoint rather than a dedicated
  // /activate route: it is one column, and a PATCH that sets it is easier to
  // reason about than two routes that can disagree about what "active" means.
  isActive: z.boolean().optional(),
  archived: z.boolean().optional(),
});

export const createDaySchema = z.object({ name });
export const updateDaySchema = z.object({ name });

export const createProgramExerciseSchema = z.object({
  exerciseId: id,
  scheme: schemeSchema,
  restSeconds: z.number().int().min(0).max(3600).nullish(),
  notes,
});
export const updateProgramExerciseSchema = z.object({
  scheme: schemeSchema.optional(),
  restSeconds: z.number().int().min(0).max(3600).nullish(),
  notes,
});

/**
 * Reordering takes the complete ordered list rather than a from/to pair. A
 * drag-and-drop UI already knows the final order, and sending it whole makes
 * the write idempotent — replaying the same request twice cannot corrupt the
 * sequence the way a relative move can.
 */
export const reorderSchema = z.object({ ids: z.array(id).min(1).max(200) });

export const programSummarySchema = z.object({
  id: z.string(),
  name: z.string(),
  notes: z.string().nullable(),
  isActive: z.boolean(),
  archivedAt: z.number().nullable(),
  createdAt: z.number(),
  dayCount: z.number().int().nonnegative(),
});
export type ProgramSummary = z.infer<typeof programSummarySchema>;

export const programExerciseSchema = z.object({
  id: z.string(),
  exerciseId: z.string(),
  name: z.string(),
  imagePath: z.string(),
  position: z.number().int().nonnegative(),
  scheme: schemeSchema,
  restSeconds: z.number().nullable(),
  notes: z.string().nullable(),
});

export const programDaySchema = z.object({
  id: z.string(),
  name: z.string(),
  position: z.number().int().nonnegative(),
  exercises: z.array(programExerciseSchema),
});

export const programDetailSchema = programSummarySchema
  .omit({ dayCount: true })
  .extend({ days: z.array(programDaySchema) });
export type ProgramDetail = z.infer<typeof programDetailSchema>;
```

- [ ] **Step 1: Implement**

`apps/api/src/lib/ownership.ts`:

```ts
import { and, eq } from "drizzle-orm";
import type { DrizzleD1Database } from "drizzle-orm/d1";
import { programDays, programExercises, programs } from "../db/schema.js";

/**
 * Every id in a request body is attacker-controlled, including ones that look
 * internal like `programDayId`. These helpers are the only sanctioned way to
 * turn one into a row: each joins back to `programs` and filters on the
 * session's own user id, so a row belonging to someone else is simply not
 * found.
 *
 * Callers turn `undefined` into a 404 rather than a 403. A 403 would confirm
 * that the id exists and belongs to somebody, which is an enumeration oracle;
 * 404 tells an attacker nothing they did not already know.
 */
export async function findOwnedProgram(
  db: DrizzleD1Database,
  userId: string,
  programId: string,
) {
  const [row] = await db
    .select()
    .from(programs)
    .where(and(eq(programs.id, programId), eq(programs.userId, userId)))
    .limit(1);
  return row;
}

export async function findOwnedDay(db: DrizzleD1Database, userId: string, dayId: string) {
  const [row] = await db
    .select({ day: programDays })
    .from(programDays)
    .innerJoin(programs, eq(programDays.programId, programs.id))
    .where(and(eq(programDays.id, dayId), eq(programs.userId, userId)))
    .limit(1);
  return row?.day;
}

export async function findOwnedProgramExercise(
  db: DrizzleD1Database,
  userId: string,
  id: string,
) {
  const [row] = await db
    .select({ entry: programExercises })
    .from(programExercises)
    .innerJoin(programDays, eq(programExercises.programDayId, programDays.id))
    .innerJoin(programs, eq(programDays.programId, programs.id))
    .where(and(eq(programExercises.id, id), eq(programs.userId, userId)))
    .limit(1);
  return row?.entry;
}
```
